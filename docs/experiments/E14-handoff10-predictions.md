## P2 — the manifest capability, anchored on the dragon · **the anchor cannot run as the dispatch describes it, and I predict that before touching it**

The dispatch says: regenerate the DRAGON's committed dense manifest with the current
code and no new declarations — byte-identical or halt. Unlike handoff 16's galleon
case, the dragon's manifest was **born under this tool at 1.3.0 with all four
declaration blocks**, so HEAD's tool should reproduce it exactly. I predict:

- **P2a — the manifest bytes come back byte-identical.** 0 bytes differing, same
  sha256, same length. This is the anchor the dispatch means and I expect it to
  hold.
- **P2b — but the anchor path as written WRITES INTO THE DRAGON'S COMMITTED TREE,
  and I register that before running it.** `e11_manifest.py:476` calls
  `build_tone_operands(tree)` unconditionally whenever a subject declares a tone
  transform, and that function `json.dump`s `tone_transform_operands.json` and
  copies two files into `_operands_sources/` **inside the subject's tree** —
  `--no-copy` does not cover it and `--out` does not redirect it. Re-emitting the
  dragon's manifest today would rewrite three files under
  `E13_stroke\export\turnaround\`, a tree the lane holds sha-verified pointers into
  and Ruling 28 makes citable-only. The bytes would very likely be identical and the
  mtimes would not, and "identical bytes" is not the property the read-only claim
  rests on.

  **The remedy I intend, stated before I write it:** extend `--no-copy` to the
  operands assembly — verify the sidecar and both sources already on disk against
  their sources by sha256 instead of rewriting them, which is the same read-only
  substitution handoff 16 made for the copies and is strictly more checking than the
  write path. If the dragon's tree does not already carry those three files, the
  anchor halts rather than creating them.

*What would falsify P2a:* any byte difference. A difference is a halt with the diff,
not a fix-up — the tool has grown one subject since the dragon was emitted, and the
whole point of the anchor is that a subject supplying no new declarations emits none.

## P8 — the contract question: does 1.3.0's `tone_transform` carry a masked per-view hue rotation? · **the reading I intend to take, registered BEFORE emitting**

**I predict the contract has an honest slot and I intend to DECLARE it**, with every
value sourced, rather than take the gap. Registered here so the reading is on the
record before the artifact exists.

The contract's own text (`lib/asset-source.js:293–329`, `docs/asset-lane-design.md`
§`asset.tone_transform`) requires `kind` (a name sdlab "does not interpret… records
and groups by"), `reference` (must resolve to a render id in this manifest) and
`operands` (a contained, hashed path); `space`, `scope`, `record` are free non-empty
strings and `reversible` is a boolean the lane records without verifying. The stated
*reason* for the block is that this lane measures colour and "an undeclared upstream
tone map is a systematic covariate sitting under every one of those numbers."

The garnet re-projection is that object: deterministic, generation-free, applied to
generated views **before** they became the projection sources these renders derive
from, and it moved hue — the exact quantity the lane's palette gate measures. Every
required field takes an honest value: `kind` `hue-rotation`, `reference` `y000_e00`,
`operands` the assembled sidecar; `space` CIELAB (the rotation is about the achromatic
axis with C\* and L preserved — the operands record C and L identical before and
after in all six rows), `scope` the stone mask on four of eight views, `reversible`
true.

**The one place it stretches, named before the ruling sees it:** the dragon's
transform was whole-figure on all eight projection sources; this one is a masked
sub-region (67,904 atlas texels = 1.854% of valid) on four of eight views, with two
further views' rotations *computed and deliberately not applied* (Ruling 26c/5's
unrotated garnet pair). `scope` is a free string and can say exactly that, and `kind`
differing from `lab-stats-transfer` means a consumer grouping by kind never conflates
the two. Declaring nothing would leave a real colour covariate undeclared under a lane
that measures colour, and 1.3.0's own lesson is that declared-null beats
omitted-null. **The reading is mine and the disposition is the advisor's** — both
alternatives go in the report and every operand rides beside the manifest either way.
